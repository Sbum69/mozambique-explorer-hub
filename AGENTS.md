- Free community activities live in `community_experiences`, never in `experiences` (business, bookable). Why: different rules (free, no booking, no price).
- Community experience photos live in the private `community-photos` bucket (path in `image_path`) and render via signed URLs. Why: public buckets are blocked and pending photos must stay private.
- Map/directions links go through `DirectionsButtons` / `directionsUrls`, never built from names. Why: no coordinates must mean no (wrong) link.
- Route visibility = is_public + status active + review_status approved; non-admin public routes are forced to pending by the `routes_review_guard` trigger. Why: user routes need admin curation.
- Plans use invoker-rights `save_route_plan` / `reset_my_route_progress`; guards require private `route-proofs` objects, matching stops and full completion, and protect plans with proofs. Why: atomic writes preserve evidence and RLS.
- Points live only in append-only `points_ledger` (DB triggers/RPCs only; reversals/redemptions negative); XP excludes redemptions; games progress only via game RPCs; badges derive (`src/lib/games.ts`). Why: clients never award points.
- Each route stop references exactly one of destination / activity / community experience, or is a titled custom stop (DB check `route_stops_one_ref`). Why: typed stops with real links only.
- Base-catalogue routes flag `requires_validation`; unlinked stops are custom `pending_validation` stops without coordinates, unvalidated day splits go in an `is_unassigned` day. Why: no invented data.
- Route covers come from one image per province (`PROVINCE_COVER_SLUG`/`provinces.cover_image`), never per-route uploads. Why: consistent, no invented images.
- Personalised discovery reads preferences only via `usePersonalPrefs` (AuthContext: profiles + profile_provinces) and splits routes with `personalizeRoutes` (province → interest/duration fit → other regions, never mixed). Why: one preference source, no hidden eligible routes.
- Onboarding stores exactly one destination province (profile_provinces = [code]; profiles.province = a destination slug in that province, else the province code). Why: single choice, and needsOnboarding/map still read profiles.province.
- Map community markers open `/community-experiences?open=<id>`; the page opens only that approved id, otherwise shows a message. Why: no community detail route, never a fallback item.
- Visitors without a session are always guests (AuthContext sets GUEST_USER; "/" redirects to /home). Why: demo/share links must open without signup; private pages still redirect to /login and RLS protects data.
- Catalogue hooks (useDestinations/useExperiences/useProvinces) share one in-flight request. Why: several components mount together and were firing duplicate queries.
- Business approval decisions go only through the admin-only `admin_decide_business` RPC (pending → approved/rejected, reason required on reject) and owner notifications come from the `businesses_notify_decision` trigger. Why: atomic, blocks stale/duplicate decisions, one notification per decision.
- Auth email redirects use `getAuthCallbackUrl()` (`src/lib/app-url.ts`) → `/auth/callback` (no query string, so it always matches the Redirect URLs allowlist); private preview hosts are never sent. The page to return to after confirming is saved at sign-up in `user_metadata.return_to` and read by the callback only if it is on the `AUTH_RETURN_PATHS` allowlist (`postConfirmTarget`), else `roleLandingTarget`. Why: preview links showed "Access denied" to non-members, and the return works even when the email is opened on another device.
- Post-login landing comes from `roleLandingTarget` (user_roles: admin → /admin, business → /business-dashboard, else onboarding/home). Why: one role-based routing rule for login and email callback.
- Business management uses authenticated server functions scoped by owner_id plus existing RLS; profile writes whitelist editable fields and preserve other contact/location keys. Why: submitted IDs cannot grant ownership or overwrite approval fields.
- Commercial public reads and new bookings require active experiences owned by approved businesses; weekly scheduling and bookings share per-activity transaction locks. Why: pending businesses cannot publish and schedule edits cannot race reservations.
- Availability edits/deletion preserve future pending/confirmed bookings and reject overlapping active weekly windows; management exposes deactivation rather than deletion. Why: preserve booking history without a duplicate scheduling system.
- Dashboards use a per-router QueryClient, owner-scoped authenticated paginated reads, and query keys with the user identity (wait for it). Why: no cross-account caches, duplicate requests or silent row caps.
- Dashboard recency means booking/business creation records, never inferred status-change events; upcoming and completion use Mozambique time. Why: no event journal exists and browser timezone must not change business rules.
- Public impact/statistics figures come only from the aggregate-only `platform_impact_stats()` RPC (counts, no rows/PII); verified impact counts only completed past bookings/routes/proofs, never money. Why: no hardcoded or unverifiable KPIs.
